# Раннер: мост между control plane и collector-framework

Дата: 2026-09-18

## Задача

У `dashboard` (control plane на Django) есть всё, кроме исполнителя: модели
`Source`/`Run`/`RunLog`/`Runner`, расписание по cron, админка и четыре HTTP-эндпоинта
под токен. Раннера нет — README прямо говорит, что он живёт рядом с парсерами.

У `collector-framework` есть всё для краулинга и намеренно нет реестра, хранилища
и планировщика: «как приложение именует парсеры — его дело».

Недостающее звено — раннер, который склеивает одно с другим. Эта спека описывает
его первую итерацию: сквозной цикл на одном парсере `quotes`.

## Рамки

**В объёме:** раннер, реестр парсеров, JSONL-хранилище, парсер `quotes`, тесты, CI.

**Вне объёма:** торговые площадки (отдельная итерация поверх готового каркаса),
дедупликация, БД на стороне раннера, запуск краулов в подпроцессах, несколько
одновременных заданий в одном раннере.

**Репозиторий:** `trading_platform`, с чистого листа на `main`. Прошлые попытки
остаются в ветках как история. Конвенции зеркалят `dashboard` — uv (`pyproject.toml`
+ `uv.lock`), `src/`-layout, `Makefile`, ruff, `.env` — два репозитория рядом
должны заводиться одинаково.

## Что даёт фреймворк

Опорные точки API, на которых стоит дизайн:

```python
open_crawler(parser_cls, *, params: dict[str, str], sink, log) -> AsyncIterator[Crawler]
crawler.stream()   # асинхронный итератор айтемов, backpressure, break останавливает краул
crawler.stats      # requests, items, errors, elapsed, reason
crawler.errors     # [(Request, Exception), ...]
exc.crawler        # упавший краул доступен с исключения
```

`log` — это `Callable[[str], Awaitable[None]]`: готовый шов под отправку строк
в `/logs/`. Сам фреймворк дополнительно пишет через stdlib `logging` (ретраи,
троттлинг, невалидные params).

## Архитектура

```
src/trading/
  parsers/
    __init__.py        REGISTRY: dict[str, type[Parser]]
    quotes.py          Quotes(Parser)
  storage/
    jsonl.py           JsonlSink
  control/
    client.py          ControlClient: claim / logs / heartbeat / complete
  runner/
    config.py          чтение окружения
    logs.py            LogBuffer + LogBufferHandler
    execute.py         выполнить один Run
    loop.py            цикл опроса
    __main__.py        python -m trading.runner
```

Три независимых куска и клей:

| Модуль | Что делает | От чего зависит |
|---|---|---|
| `parsers` | описывают, как парсить сайт | только `collector` |
| `storage` | принимает dict, отдаёт путь к файлу | ничего |
| `control` | говорит с control plane по HTTP | `httpx` |
| `runner` | склеивает три предыдущих | все |

`parsers` не знает ни про control plane, ни про хранилище. `control.client` не знает
про краулинг. `storage` не знает, откуда взялся dict.

## Ключевое решение: парсеры остаются чистыми

`process_item()` не переопределяется, `sink=` фреймворку не передаётся. Айтемы
вычерпывает раннер:

```python
async with open_crawler(parser_cls, params=params, log=buffer.log) as crawler:
    async for item in crawler.stream():
        sink.write(item)
```

Парсер тогда — буквально то, что человек пишет по документации фреймворка, без
обвязки. Решение «куда писать» живёт в одном месте, а не размазано по тридцати
парсерам. Это прямая правка того, что развалилось в прошлых попытках.

## Реестр

`parsers/__init__.py` держит явный словарь:

```python
REGISTRY: dict[str, type[Parser]] = {'quotes': Quotes}
```

Ключ словаря — публичный контракт с админкой (поле `Source.parser`), а не путь
в Python. Класс можно переименовать, не трогая данные в БД control plane.
Неизвестный ключ даёт мгновенный отказ с внятным сообщением, а не `ImportError`
из недр импорта.

Автодискавери по подклассам отвергнуто: импорт-сайдэффекты и молчаливые коллизии
имён, а «почему парсер не виден» — худший жанр отладки.

### Граница «новый класс» против «новый Source»

- Меняется **как парсить** (селекторы, обход, `start_urls`) — новый класс, новая
  строка реестра.
- Меняется **насколько напористо** (`concurrency`, `max_requests`) — тот же класс,
  другой `Source` с другими `params`.

## Поток данных

```
claim --> {id, source, parser, params, log_level, trigger, lease_expires_at}
   |
   |-- REGISTRY[parser]                     неизвестен -> failed
   |-- JsonlSink -> data/<source>/<run_id>.jsonl
   |-- asyncio-задача: heartbeat каждые lease/3
   |-- asyncio-задача: шипер логов, пачками <= 500 или раз в 2 с
   `-- complete <-- counters + result_locator
```

Раннер асинхронный целиком (`httpx.AsyncClient`): шов `log=` у фреймворка async,
а heartbeat обязан идти *во время* краула. Синхронный клиент пришлось бы
заворачивать в потоки.

Один раннер выполняет одно задание за раз. Параллелизм внутри краула даёт
`Settings.concurrency`; параллелизм по источникам — это второй запущенный раннер
со своим токеном.

### Приведение params

`Source.params` в админке — произвольный JSON, фреймворк ждёт `dict[str, str]`.
На границе `execute.py` скаляры (`int`, `float`, `bool`, `str`) приводятся
к строкам: `{"concurrency": 2}` -> `{"concurrency": "2"}`. `bool` даёт `"true"` /
`"false"` в нижнем регистре. Вложенные структуры (списки, словари, `null`)
передаются как есть — их читает сам парсер через `ctx.params`, фреймворк в них
не заглядывает.

Без приведения `read_concurrency` молча свалится в дефолт и напишет
`params.bad_concurrency` в лог — отлаживать такое неприятно.

### Логи

Два источника, один буфер:

1. Хук `log=` — строки самого парсера.
2. `LogBufferHandler`, навешанный на логгер `collector` — ретраи, троттлинг,
   битые params.

Буфер — список под `threading.Lock` (`logging.Handler` вызывается синхронно и
потенциально из другого потока), шипер вычерпывает его асинхронной задачей.

Хук `log=` отдаёт голую строку без уровня — такие записи получают `INFO`.
У записей из `logging` уровень берётся из `LogRecord`. Фильтр по `log_level`
из задания применяется к обоим источникам уже после того, как уровень проставлен.

Клиент шлёт `{"ts": ISO8601 с таймзоной, "level": ..., "message": ..., "context": {}}`.
Поле `seq` проставляет сервер. Ограничения control plane соблюдаются на клиенте:
пачка не больше 500 строк (`MAX_LOG_BATCH`). Обрезку длины и лимит 10 000 строк
на запуск сервер обеспечивает сам.

**Данные в логи не попадают** — только счётчики, идентификаторы и URL. Иначе
спарсенное просочится в control plane через чёрный ход.

### Счётчики

| Поле `complete` | Источник |
|---|---|
| `items_total` | `stats.items` |
| `items_new` | `0` |
| `items_updated` | `0` |
| `counters.requests` | `stats.requests` |
| `counters.errors` | `stats.errors` |
| `counters.elapsed` | `stats.elapsed` |
| `counters.reason` | `stats.reason` |

`items_new` и `items_updated` — нули осознанно: JSONL не дедуплицирует, врать
нечем. Появятся, когда появится хранилище, которое знает про прошлые запуски.

`elapsed` — чистое время краула. Длительность control plane считает сам по
`started_at`/`finished_at`, там ещё сеть и очередь; расхождение между ними само
по себе диагностика.

### Хранилище

`data/<source_slug>/<run_id>.jsonl`, одна строка на айтем, `ensure_ascii=False`.
Каталог — по slug источника, а не по имени парсера: один парсер под двумя
расписаниями не смешает выдачу.

Пишем в `<run_id>.jsonl.part`, по завершении краула переименовываем. Так файл
без суффикса всегда означает «краул дошёл до конца». При отказе `.part`
остаётся на диске и его путь всё равно уходит в `result_locator` — частичные
данные лучше молчания.

`result_locator` — абсолютный путь; до 500 символов его обрезает сервер.

## Отказы

| Ситуация | Поведение |
|---|---|
| Неизвестный ключ парсера | `failed`; `error` называет ключ и перечисляет известные |
| Краул бросил исключение | `failed`; `error` — тип, сообщение и `len(exc.crawler.errors)`; уже записанные айтемы сохраняются, `result_locator` отдаётся |
| `stats.reason == 'max_requests'` | `success` + WARNING в ленту: упёрлись в предохранитель, данные могут быть неполными |
| `stats.reason == 'cancelled'` | не возникает: раннер дочитывает `stream()` до конца |
| Control plane недоступен при `claim` | цикл не падает: сообщение в stderr, пауза `poll_interval`, следующая попытка |
| Control plane недоступен при `complete` | три попытки с нарастающей паузой, затем сдаёмся — задание протухнет по аренде |
| Отправка пачки логов не прошла | пачка теряется, краул продолжается; логи не важнее данных |
| SIGINT / Ctrl+C во время запуска | краул останавливается, `complete` со статусом `failed` и текстом «прерван оператором» |
| Раннер убит жёстко (SIGKILL) | ничего не делаем: на то у control plane аренда и статус `expired` |

Аренда: heartbeat каждые `lease_seconds / 3`, отсчитывая от `lease_expires_at`
из ответа `claim`. Отправка логов тоже продлевает аренду — это сервер делает сам.

## Конфигурация

Читается из окружения, локально — из `.env` (как в `dashboard`).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CONTROL_URL` | `http://127.0.0.1:8000` | адрес control plane |
| `RUNNER_TOKEN` | — | обязательна; токен из админки |
| `DATA_DIR` | `data` | корень для JSONL |
| `POLL_INTERVAL` | `10` | запасной интервал, если ответ `claim` его не дал |
| `HTTP_TIMEOUT` | `30` | таймаут запросов к control plane |
| `LOG_FLUSH_SECONDS` | `2` | как часто шипер отдаёт накопленное |

Отсутствие `RUNNER_TOKEN` — падение на старте с внятным сообщением, а не 401
на первом же опросе.

## Тесты

**Юниты:**

- реестр: известный ключ отдаёт класс, неизвестный даёт ошибку со списком известных;
- `LogBuffer`: разбиение на пачки по 500, фильтр по уровню, потокобезопасность,
  пустой буфер не порождает запрос;
- приведение params: скаляры в строки, `bool` в `"true"`/`"false"`, вложенное — как есть;
- `JsonlSink`: путь по slug и run_id, `.part` -> rename, кириллица без escape;
- маппинг `stats` -> `counters`.

**Интеграционный, без сети:** `httpx.MockTransport` изображает control plane,
парсер ходит на локальную фикстуру. Проверяется полный цикл: claim -> запись
айтемов -> пачки логов -> complete с правильными счётчиками. Отдельным кейсом —
путь отказа: падающий парсер закрывает запуск как `failed` и всё равно отдаёт
`result_locator`.

Сеть в тестах не используется: `quotes.toscrape.com` в CI — это флак.

**CI:** копия `dashboard` — GitHub Actions, `uv sync --locked`, `ruff check` +
`ruff format --check`, тесты.

## Ручная проверка

1. В админке `dashboard`: Раннеры -> создать, скопировать токен.
2. Источник: `парсер = quotes`, cron `*/5 * * * *`, params пустые.
3. В `trading_platform`: `.env` с `RUNNER_TOKEN`, затем `make run`.
4. Кнопка «Запустить сейчас» -> запуск появляется, лента лога наполняется
   в реальном времени, по завершении статус `success`, «получено» больше нуля,
   «результат» указывает на файл, файл содержит цитаты в UTF-8.

## Открытые вопросы на потом

- Дедупликация и `items_new`/`items_updated` — когда появится хранилище с памятью.
- Подпроцесс на запуск — когда парсеров станет много и утечки начнут копиться.
  Граница для этого уже есть: `execute.py` выполняет ровно один `Run`.
- Торговые площадки из ветки `claude/tender-goldberg-pgdvy3` — следующая итерация.

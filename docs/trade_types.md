# Тип торгов и обновление существующих документов

`trade_type` — понятное полное название. Явный текст страницы сохраняется
целиком, включая «(Банкротство)» и «(ГК РФ)»; чистятся только пробелы.
Общие условия btorg теперь запрашиваются перед AJAX-фрагментом лотов.
Rus-on читает «Тип торгов» со страницы торгов, Kendo — явную подпись или
пояснение в «Номер торгов». iTender использует полное название листинга;
при сохранении деталей подписанные сведения имеют приоритет.

| Поле Mongo | Значение |
|---|---|
| `trade_type` | Полное название; неизвестный код остаётся кодом |
| `trade_type_raw` | Исходный текст или весь суффикс номера, включая `-К` и пояснение |
| `trade_type_code` | Код, если найден; сохраняется и при противоречащем явном тексте |
| `trade_type_source` | Источник основного значения: `listing:number`, `listing:Тип торгов`, `page:<подпись>` |
| `trade_kind` | `публичное предложение`, `аукцион`, `конкурс`, иначе `null` |
| `trade_participation` | `открытая`, `закрытая`, иначе `null` |
| `trade_price_form` | `открытая`, `закрытая`, иначе `null` |

Открытая форма цены не означает открытый доступ участников. Если участие
не указано, оно остаётся `null`. Отдельные подписанные формы участия и цены
в деталях iTender приоритетнее признаков из общего названия. Исходные поля
форм остаются в `detail`. Название не сокращается до `trade_kind`.

При отсутствии явного текста используется подтверждённый словарь:
`ОАОФ`, `ОАЗФ`, `ЗАОФ`, `ЗАЗФ`, `ОКОФ`, `ОКЗФ`, `ЗКОФ`, `ЗКЗФ`, `ОТПП`, `ЗТПП`.
Подтверждение — полные пояснения в `detail.Номер торгов` семи коллекций
Kendo, проверенные 2026-10-03. Например, `ОАЗФ` — открытый аукцион с закрытой
формой цены, `ЗКОФ` — закрытый конкурс с открытой формой цены.
`ППК`, `КТПП`, `КАОФ` и другие неизвестные коды не расшифровываются.
В `ОТПП-К` известна основная часть `ОТПП`; смысл модификатора `К` не выводится.

## Проверенные причины пропусков

На текущей странице el_torg `trade_nid=113964` есть «Тип торгов:
Публичное предложение», но нет кода в листинговом номере. Это закрывает
прежний путь потери типа. Страница сохранена в регрессионной фикстуре.

Три документа ausib имеют номера `16539-ОТПП-К`, `16324-ОТПП-К`,
`16238-ОАОФ-К`. Условие разбиения на ровно две части давало `null`.
Теперь суффикс сохраняется целиком, а явное поле
«Форма проведения торгов и подачи предложений» приоритетнее кода.
Фикстура `id=104661680` проверяет сохранение полного названия
«Открытый аукцион с открытой формой представления предложений о цене (Банкротство)».

## Mongo: сначала план, затем применение

Обычный crawl исправляет только встретившиеся в листинге лоты. Обычный
detail обходит только очередь; завершённые архивные лоты так не обновить.
Для существующей базы предусмотрен `tp.scripts.trade_types`.

Из корня `trading_platform`, с текущими настройками `MONGO_URI` и `MONGO_DB`:

```powershell
# Небольшой план, читает Mongo, обращается к страницам, базы не изменяет.
uv run python -m tp.scripts.trade_types plan ausib el_torg --refresh-pages --limit 5 --output trade-types-sample.jsonl

# План для всех документов: использует сохранённые детали, затем прежний тип/номер.
uv run python -m tp.scripts.trade_types plan --output trade-types-cached.jsonl

# Полная проверка первоисточников наиболее проблемных движков, включая архивные лоты.
uv run python -m tp.scripts.trade_types plan btorg ruson --refresh-pages --output trade-types-pages.jsonl

# Только после просмотра выбранного плана и резервного копирования базы:
uv run python -m tp.scripts.trade_types apply --plan trade-types-cached.jsonl
```

`plan` не пишет в Mongo и не перезаписывает существующий файл. В каждой
строке BSON Extended JSON сохранены `_id`, `source`, прежние поля `before`
и новые `after`. Отсутствующее поле отличается от `null`. Ошибки страниц
не попадают в план; итог содержит число ошибок и неизвестных/пустых видов.
GET делается один раз на URL за площадку, с паузой `DELAY` и HTTP_TIMEOUT.
Этот вспомогательный загрузчик использует стандартный urllib с cookies и
проверкой TLS; специальные HTTP-хуки и сертификаты краулеров он не повторяет.
Если площадка требует такой настройки, её ошибки нужно разобрать отдельно,
а не отключать проверку TLS и не считать её документы восстановленными.

`apply` меняет исключительно семь полей типа, без удаления документов,
изменения `detail`, статусов, цен, кадастровых номеров и временных меток.
Если прежние поля типа уже изменились, документ пропускается; повторное
применение плана ничего не переписывает. Файл `before` — резервная копия
затронутых полей; для полного восстановления остальных данных нужен обычный
backup Mongo. Не запускайте crawler/detail одновременно с применением.

Планы следует применять последовательно: сначала cached, затем заново
составить pages относительно обновлённой базы и применить pages.
Свежая страница тогда заменит прежний текст/код. Нельзя заранее составить
оба плана и ожидать, что второй применится поверх первого: защита `before`
пропустит изменившиеся документы. Для el_torg без сохранённого общего поля
cached-плана недостаточно — нужен `--refresh-pages`.

Скрипт восстановления не запускается автоматически. В рамках исправления
массовая запись в рабочую `trading` не выполнялась.

## PostGIS после Mongo

В `G:\hub\geo-info\elt\cadastre_etl` текущий ETL переносит верхнеуровневый
`trade_type` прямо в `trading.lot.trade_type`. Поэтому дополнительных
изменений ETL для полного названия не требуется. После завершения и
проверки обновления Mongo:

```powershell
Set-Location G:\hub\geo-info\elt\cadastre_etl
uv run cadastre-etl sync --full
```

Нужен именно `--full`: восстановление не сдвигает `updated_at`/`detail_at`,
а инкрементальный ETL выбирает документы по этим меткам. Upsert выполняется
по `(source, lot_id)` и сохраняет `geom`; переносит только лоты с кадастровыми
номерами. Для пробы можно сначала выполнить `sync ausib --full`.
Новые отдельные признаки и исходный код остаются в Mongo: в текущей модели
PostGIS для них нет колонок. Если они нужны отдельными фильтрами в PostGIS,
потребуется отдельная миграция схемы и ETL; это исправление её не выполняет.

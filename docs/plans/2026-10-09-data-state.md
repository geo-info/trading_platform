# Согласованность состояния данных

Основание: архитектурный обзор от 09.10.2026 и разрешение пользователя
внести исправления после снимка проекта `fb7c65f`.

## Контракт

Сохраняем структуру четырёх движков и API Store. Чистые функции принимают
решения об объединении листинга и деталей; Mongo выполняет запись с проверкой
ревизии. Исходные наблюдения не подменяются производными полями.
Неизвестный статус не означает действующие торги. Пустой ответ не означает
успешное получение деталей. Частичный обход не означает полный сбор.

Аналитические поля: цена, даты, статус, вид торгов, участие, форма цены,
описание и идентификаторы объекта. Служебные: источник и ссылки, исходный
листинг/detail, время наблюдения и записи, ревизия, версия преобразования,
состояние деталей и противоречия. Служебные поля необходимы для доверия
к аналитическим данным, но не должны становиться признаками рыночного анализа.

## План и проверка

- [x] Регрессии: повторный листинг после деталей, конкурентные обновления,
  запоздавшие детали, неизвестный статус, заглушка iTender, частичный результат.
- [x] Чистые правила объединения, атомарная запись с CAS, отдельные часы
  изменения листинга и содержимого, явное состояние отсутствующих деталей.
- [x] Общая модель iTender, неопределённый статус, проверка структуры детали,
  фиксация противоречий типа торгов и неполного обхода.
- [x] Документация контракта, процедуры нового сбора и допуска в PostGIS.
- [x] pytest с обязательной временной Mongo, Ruff, независимый обзор изменений.

Ограничения: production Mongo и PostGIS не изменять; LIMIT=1000 сохранить.
Полный журнал HTML и геометрия требуют отдельного этапа, не добавляются здесь.
Связанный ETL не изменяем: несовместимости его текущих преобразований явно
описываем как условие перед переносом. Работа в запрошенной ветке текущего
репозитория; дополнительный worktree не нужен.

## Итог выполнения

Проверены RED→GREEN регрессии: явный тип после повторного листинга,
запоздавшие детали, неизвестный статус, HTML-заглушка и частичный результат.
Итог: 196 passed, 4 live deselected при REQUIRE_MONGO=1; Ruff check и
format --check успешны, git diff --check без замечаний относительно снимка.
Независимый обзор указал на несовместимость параллельного apply старой
миграции с CAS. Принято существующее документированное ограничение:
миграция выполняется только при остановленных парсерах. Это инструмент
разового восстановления старых документов, для очищенной базы не нужен.

Решение: сохранить консервативный detail_at начала прогона и описать его
точный смысл. Точный timestamp HTTP-ответа и постоянный журнал ошибок лотов
не добавлены. Это не мешает обнаруживать устаревшие детали через очередь,
но ограничивает прослеживаемость; полный аудит нового сбора ещё предстоит.

Ветка остаётся локальной, без merge/push. Изменения ETL и массовые операции
с базами не выполнялись. Следующий этап: пользовательский повторный сбор,
затем аудит по docs/data_contract.md и согласование ETL перед PostGIS.

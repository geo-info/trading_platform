# Данные анализа и сведения об их получении

Все четыре движка формируют `Lot`. Исходные строки остаются рядом с
разобранными значениями. Полное название торгов не заменяется кодом.

| Назначение | Поля и правила |
|---|---|
| Анализ торгов | `price`, `price_value`, `status`, `is_active`, даты, `trade_type`, `trade_kind`, `trade_participation`, `trade_price_form` |
| Идентичность | `(source, lot_id)` — один лот. Кадастровый номер не является ключом лота |
| Проверка источника | `lot_url`, `trade_url`, `listing` — последнее наблюдение листинга, `detail` — последние принятые детали, исходные текст и код типа |
| Изменение содержимого | `updated_at` — время записи изменившегося листинга или деталей; записывается атомарно с данными |
| Повторное наблюдение | `last_seen_at` — время приёма листинга хранилищем, даже если содержимое прежнее |
| Очередь деталей | `listing_changed_at` — изменение листинга; `detail_at` — нижняя граница времени запроса деталей |
| Диагностика записи | `written_at`, `revision`, `normalization_version=2` |
| Неопределённость | `is_active=null` при неизвестном статусе, `detail_state`, `trade_type_conflicts` |

`created_at` — первая запись в Mongo. Метки сохраняются в UTC. Даты источника
без указанного часового пояса по прежнему контракту интерпретируются как
Europe/Moscow; это допущение, а не подтверждение часового пояса площадки.
`detail_at` сейчас равен началу детального прогона. Это консервативная граница:
изменение листинга во время прогона оставляет лот в очереди на повторную проверку.
Она не выдаётся за точное время получения HTTP-ответа.

`detail_state=found` означает, что принята узнаваемая страница деталей;
`not_found` — страница торгов распознана, но конкретный лот отсутствует.
При `not_found` прежний `detail` сохраняется как историческое свидетельство,
а не актуальное содержимое. Новый лот имеет `pending`. Ошибка запроса или
разметки не меняет успешное наблюдение и не снимает лот с очереди; ошибка
видна в журнале и результате запуска. Отдельного постоянного журнала ошибок
каждого лота в этой версии нет. Свежесть деталей определяется очередью,
а не одним значением `found`.

Повторный неизменившийся тип листинга не вытесняет тип из деталей. Изменение
самого типа/номера в листинге отменяет прежнее обогащение; требуется новый
detail. Одновременные записи проверяют `revision` и при конфликте пересчитывают
изменение. До 20 попыток, затем явная ошибка запуска. Старый ответ деталей
не вытесняет ответ более нового запроса.

Отдельное подписанное значение формы цены/участия приоритетнее общего
названия. Противоречие сохраняется в `trade_type_conflicts` с полем, обоими
значениями и подписью источника. `trade_type_raw` и название сохраняют текст
страницы: это свидетельство источника, а не автоматически исправленная фраза.

## Новый сбор и проверка качества

Рабочая Mongo очищена пользователем. Начинать следует обычным сбором:

```powershell
uv run python -m tp.scripts.crawl --max-pages 100
uv run python -m tp.scripts.detail --limit 0
```

Это инструкции, команды автоматически не запускались. `--limit 0` — вся
очередь; по умолчанию сохранён пользовательский предел 1000. Если листинг
имеет следующую страницу за пределом `max_pages`, результат будет `partial`.
Увеличьте предел и повторите обход: upsert не создаёт копий лота.
`complete` означает завершение доступного обхода, а не доказательство наличия
всего архива площадки. Ошибки и намеренно ограниченный обход дают код выхода 1.

После сбора нужен отдельный отчёт по всем восьми требованиям:

1. **Точность:** стратифицированная сверка цены, статуса, дат и кадастровых
   номеров с источниками каждой площадки; геометрию проверять уже на этапе
   обогащения. Регрессионные HTML не доказывают точность всех новых лотов.
2. **Полнота:** доли `null` по площадкам и отдельно по лотам с кадастровыми
   номерами; не считать ноль отсутствием значения.
3. **Актуальность:** распределения `last_seen_at`, `updated_at`, очередь деталей,
   даты источника и неполные запуски. Старый статус не доказывает активность сегодня.
4. **Согласованность:** конфликты типа, порядок дат, согласование цены и валюты,
   проверка допущения о часовом поясе каждой площадки.
5. **Уникальность:** ключ `(source, lot_id)` и повторный сбор без прироста
   дублей. Один кадастровый номер в нескольких торгах допустим.
6. **Валидность:** формат и смысл кадастровых номеров, цен, дат; геометрия —
   отдельно с проверкой типа, CRS, пригодности и принадлежности объекту.
7. **Прослеживаемость:** доступность ссылок, исходных строк и версии правил.
   Здесь хранится последнее наблюдение, не полный журнал HTML/преобразований.
8. **Неопределённость:** отдельно неизвестный статус, отсутствие лота, очередь
   и ошибки запуска; отсутствие геометрии не смешивать с ошибкой её запроса.

Этот отчёт ещё не выполнен на новом сборе. До него оценка качества новых
данных и разрешение на перенос в PostGIS не подразумеваются.

## Совместимость с cadastre_etl

ETL уже копирует верхнеуровневый `trade_type`. Однако он заново вычисляет
`is_active` по старому правилу и использует non-null bool в схеме/модели.
Перед переносом нужно поддержать трёхзначную активность и согласовать
нормализованные поля. Иначе неизвестные статусы снова станут активными.
Новые поля типа, конфликтов и происхождения пока не имеют колонок PostGIS.
Связанный репозиторий в этой задаче не изменялся.

После проверки Mongo и исправления указанного контракта ETL можно выполнить
`uv run cadastre-etl sync --full` из `G:\hub\geo-info\elt\cadastre_etl`.
Полный проход нужен после пересборки Mongo и для старых планов исправления
типов; прежний watermark не должен определять полноту нового набора.
Отдельно сверить старые строки PostGIS: upsert не является удалением лотов,
которые не попали в новый сбор. Геометрию не стирать при обновлении торгов.
